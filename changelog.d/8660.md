---
synopsis: "`cabal haddock Foo.Bar` documents just that module"
packages: [Cabal, cabal-install]
issues: 8660
---

A module or file target given to `cabal haddock`, such as
`cabal haddock Foo.Bar`, `cabal haddock lib:pkg:Foo.Bar` or
`cabal haddock src/Foo/Bar.hs`, now runs Haddock on that module rather than
on the whole component it belongs to as `cabal build` does. Package and
component targets behave as before.

The page is regenerated in place, in the component's documentation directory,
so its links to sibling modules and to dependencies keep working. Haddock also
regenerates, with identical content, the pages of the modules of the component
that the target imports, since it processes every module reachable from its
target, so the time saved depends on the module's imports rather than on the
size of the component. Haddock is told to use the existing contents and index
pages, not to rewrite the `.haddock` interface file and not to regenerate the
quickjump index, so those keep describing the whole component. A targeted
`other-modules` entry is not hidden.

`Setup.hs haddock` honours the same module and file targets instead of dropping
them with a warning. `TargetInfo` gains the `targetSub` field holding the
module or file of a target, which `readTargetInfos` now fills in rather than
discarding; the commands that process whole components drop it with the usual
warning through the new `wholeComponentTargets`. Custom setups built against a
Cabal library of version 3.18.* or earlier still document the whole component.
