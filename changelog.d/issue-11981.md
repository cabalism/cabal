---
synopsis: "`repl` honours `--enable-library-bytecode`"
packages: [Cabal]
prs:
issues: 11981
---

With `--enable-library-bytecode`, `repl` now bases its GHC invocation on the
compiler's own build way (for a dynamically linked GHC that is `-dynamic
-hisuf dyn_hi -osuf dyn_o`) and passes `-fbyte-code -fwrite-interface
-fwrite-byte-code`. GHCi then writes `.gbc` files into the build directory
and reuses them, and those written by `build`, instead of recompiling the
component's modules from source on every start. Previously the repl always
used the static way's options, so on a dynamically linked GHC the interface
files it read had the wrong way tag and the bytecode files were discarded.
To keep the recompilation fingerprints of `build` and `repl` in step, a
`build` with bytecode enabled now compiles the static-and-dynamic pass with
`-fPIC`, as a dynamically linked GHCi always does.

Bytecode objects are now only produced when building library components.
Executables, test suites and benchmarks produced `.gbc` files that nothing
used, and a profiled-only executable failed with a spurious "standalone
bytecode" error.
