A package version can now be pinned to a specific `.cabal` file revision, so
that later revisions of the package cannot change the build plan without
freezing the whole index with `index-state`. The revision is written in the
notation Stack uses: `@rev:N` selects it by number (the `x-revision` field, the
original upload being revision 0) and `@sha256:HASH` by the hash of the
`.cabal` file text, as reported in `plan.json`.

A pin can be given in two places:

- in an exact version constraint, `constraints: foo ==1.2.3@rev:2`, which fixes
  the version and pins the revision. The pin is only accepted together with an
  exact version (`==`) and in the unqualified or `any.` scope, since a revision
  applies to the package version wherever it is used. This also works on the
  command line, `--constraint="foo ==1.2.3@rev:2"`;
- in the new `revisions` project field, `revisions: foo-1.2.3@rev:2`, which
  pins the revision without constraining the version: the pin only applies when
  the solver picks that package version, and a warning points out a pin that
  has no effect because another version was picked. There is deliberately no
  `--revisions` command line flag, because `--constraint` already provides the
  command line form and a second spelling of the same thing would only add to
  the surface area.

It is an error when the package version exists in a package repository but
none of its revisions match the pin, or when a package version is pinned to
two different revisions.

`cabal freeze` now also pins the revision of every package in the plan whose
`.cabal` file is a revision, in its version constraint
(`any.foo ==1.2.3@rev:2`), so a freeze file is no longer affected by
later revisions of its packages.

With a project depending on `smtlib-backends ==0.3` (three revisions on
Hackage) and `allow-newer: smtlib-backends:base` in `cabal.project`:

- `cabal build --dry-run`: `dist-newstyle/cache/plan.json` shows
  `"pkg-revision": 2` for `smtlib-backends-0.3`.
- Add `revisions: smtlib-backends-0.3@rev:0` to `cabal.project` and rebuild:
  `"pkg-revision": 0`.
- `cabal build --dry-run --constraint="smtlib-backends ==0.3@sha256:69977f97a8db2c11e97bde92fff7e86e793c1fb23827b284bf89938ee463fbf0"`:
  `"pkg-revision": 1`.
- `cabal build --dry-run --constraint="smtlib-backends ==0.3@rev:99"`: fails
  with `[Cabal-7169]`, listing revisions 0, 1 and 2 with their hashes and
  naming the command line constraint as the source of the pin.
- With `revisions: smtlib-backends-0.3@rev:0` in `cabal.project`,
  `cabal build --dry-run --constraint="smtlib-backends ==0.3@rev:1"`: fails
  with `[Cabal-7170]`, naming both the field and the constraint.
- `cabal freeze`: `cabal.project.freeze` contains
  `any.smtlib-backends ==0.3@rev:2` and no `revisions` field.
- `cabal build --dry-run --constraint="smtlib-backends >=0.3@rev:1"` and
  `--constraint="setup.smtlib-backends ==0.3@rev:1"` are rejected, explaining
  that a pin needs an exact version and an unqualified or `any.` scope.

## Draft pull request description

**Fixes #7833: pin package revisions in `constraints:` and with a `revisions:` project field**

### Motivation

Hackage revisions can change a build plan after the fact, and today the only
defence is `index-state`, which freezes the *entire* index:

- A revision that tightens bounds can break a previously working plan —
  hasufell's production incident in #7833, and the `QuickCheck` revision that
  broke CI in #7277 ("freeze should freeze either the index or the revisions").
- `index-state` is all-or-nothing: you cannot bump the index to get new packages
  while keeping one known-good revision, and "managing to pick your index state
  in a way that it touches exactly a set of specific revisions is impossible in
  the general case" (#7833).
- Freeze files today don't protect against revisions at all (#7277);
  `allow-newer: all` on top of a freeze file was suggested as a workaround but
  doesn't cover revisions that add dependencies.
- The information already exists: `cabal-install` keeps every revision in its
  index cache and `plan.json` reports `pkg-revision` and `pkg-cabal-sha256`
  (#5695), but there is no way to feed a choice back in. Stack has had
  `pkg-1.2.3@rev:N` / `@sha256:…` for years.

The thread's consensus was: not in `build-depends` (revisions are a metadata
mechanism, not a package property), but acceptable in project configuration —
@gbaz "potentially feasible, though it would take some care", @andreabedini
"somewhere in cabal.project, maybe", @Mikolaj "the Stack notation looks like a
good choice". This PR does exactly that.

### What this adds

Revision pins in Stack notation, `@rev:N` (the `x-revision` number, original
upload = 0, as `plan.json` reports it) or `@sha256:HASH` (hash of the `.cabal`
text, also as in `plan.json`), in two places:

1. **In an exact version constraint** — `constraints: foo ==1.2.3@rev:2`, and
   therefore `--constraint="foo ==1.2.3@rev:2"` on the command line. Accepted
   only with `==` and in the unqualified or `any.` scope, since a revision
   applies to the package version wherever it is used.
2. **A `revisions:` project field** — `revisions: foo-1.2.3@rev:2`, which pins
   without constraining the version (inert if the solver picks another
   version). No dedicated command-line flag: `--constraint` already is the
   command-line form (see changelog).

`cabal freeze` now writes `any.foo ==1.2.3@rev:N` for every package in the plan
whose `.cabal` is a revision, so a freeze file is no longer changed by later
revisions.

### Design notes (for reviewers)

- **No solver changes.** Pinning is an index-read operation: `01-index.tar` is
  append-only and `packageListFromCache` already collapses revisions with
  last-write-wins; a pin just selects a different entry after `index-state`
  filtering. The constraint form desugars to `==` for the solver plus a pin.
  The index cache format is unchanged.
- **Hard error** when a package version exists but no revision matches (lists
  the available `rev:N (sha256:…)`), or when two pins conflict; both name where
  each pin came from (field/constraint, project file/command line/freeze).
- `rev:N` is defined by the `x-revision` field rather than index position, so
  it agrees with `plan.json` and Hackage's revisions page.
